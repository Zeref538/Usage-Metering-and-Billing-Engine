Count Once

Usage Metering & Billing Engine

Every paid API has to answer three questions on every request: how much has this customer used, what does it cost, and have they hit their limit. Get any of them wrong and you either lose money or bill someone twice. This backend answers all three, and keeps plans in sync with Stripe.

FastAPI and PostgreSQL. Idempotency keys checked under a per-tenant row lock with a UNIQUE backstop, quotas that answer 402 or 429 honestly, token pricing in integer micro-dollars with the cached-input and reasoning rules, and Stripe test-mode webhooks verified on the raw body and deduplicated by event id, applied by a worker with backoff retries.

02Exactly once

A retried request is never billed twice

Idempotency keys under a per-tenant row lock, UNIQUE as the backstop

Networks drop answers. A client that never heard back sends the same request again, and a careless backend bills it twice. Here every request carries a label, an idempotency key. The same label with the same body gets the first answer back, word for word, and nothing new is recorded. The same label with a different body is refused.

metering.record() takes SELECT ... FOR UPDATE on the tenant row for the whole decision: key lookup, quota check, insert. A replay with the same body returns the stored response byte for byte with Idempotent-Replayed: true; a different body is a 422. UNIQUE (tenant_id, idempotency_key) backs it up. Responses are stored as json, not jsonb, because jsonb reorders keys and the replay stopped being byte-identical. 

HTTP/1.1 201 Created
{"event_id":3008, ... "cost":{"micros":2050,"usd":"0.002050"}, ...}

HTTP/1.1 201 Created
idempotent-replayed: true
{"event_id":3008, ... "cost":{"micros":2050,"usd":"0.002050"}, ...}

From docs/curl-retry.txt: the same key sent twice, the same event id back, one event stored.

03Honest limits

402 when upgrading helps, 429 when it does not

Allowed while used + requested ≤ limit; the refusal says which limit and when it resets

Call 1,000 on the Free plan succeeds. Call 1,001 is refused, and a refused request records nothing, so retrying it with the same key after upgrading works. The answer depends on whether paying would help:

04Pricing tokens

Cached input is part of input, and reasoning is output

Integer micro-dollars, per-event half-up rounding, monthly total priced once

AI providers report tokens in a way that is easy to misread. The cached tokens are already inside the input count, not extra. The model's hidden thinking, reasoning tokens, is billed like output. Add all four numbers together and price them as input, and the bill comes out at less than half of what it should be.

Fresh input is input_tokens - cached_input_tokens. Reasoning is billed at the output rate. One event is rounded half-up to a whole micro-dollar; the monthly figure on /usage is priced from the month's summed counts and rounded once, so per-event rounding cannot drift the total, with the per-event sum shown beside it.

TokensPrice per 1MWorked example

output and reasoning (1,500 + 2,500)$2.5010,000 µ$

plus the API call$0.0002 each200 µ$

Summing all four counts and pricing them as input gives 5,400 micro-dollars, less than half. The token quota counts 14,000: input plus output plus reasoning, with cached counted once, not twice. Probe 5 checks exactly this request end to end.

05Stripe

Only signed, new events can change a plan

Signature verified on the raw body, deduplicated by event id, applied by a retrying worker

When someone pays, Stripe sends a message to the backend. Anyone could send a fake one, and Stripe sometimes sends the same one twice. So each message is checked against a shared secret before anything happens, every message id is stored once, and a background worker applies it. A message that fails is retried, then raised as an alert.

The signature is verified on the raw request body (forged: 400, nothing stored), then INSERT ... ON CONFLICT (event id) DO NOTHING turns replays into "duplicate". The worker applies events so the tenant mirrors Stripe, and an older event cannot undo a newer one. Failures retry after 2, 4, 8 and 16 s; after 5 tries the event is marked failed with an alert row and an ERROR log.

The real test-mode run, read back from the database afterwards (ids shortened):

Stripe eventStatusNote
checkout.session.completeddonesubscription active: tenant 1 is now pro

06What it cannot tell you

Built for one paid plan and one lock per customer

Limits, stated before anyone asks

  • One paid plan. "Any active subscription" means Pro. A second tier needs a price-to-plan map.
  • Subscriptions made outside Checkout do not change a plan until their first update, because customer.subscription.created is ignored.
  • Calendar months in UTC, not per-customer billing cycles.
  • The row lock serialises each customer. Fine at this scale; a very busy customer would want a counter table or sharded keys.
  • Refused requests are not stored under their key, unlike Stripe's own API. That is on purpose, so a retry after upgrading works.
  • No invoices, proration or overage billing, the brief's stretch goals.
07Run it yourself

Run it yourself

Needs only Docker. The demo keys are in .env.example; Stripe is optional and test mode only.

git clone https://github.com/Zeref538/Usage-Metering-and-Billing-Engine
cd Usage-Metering-and-Billing-Engine
cp .env.example .env
docker compose up -d --build --wait
docker compose exec api python -m app.seed --reset
python scripts/probes.py
docker compose exec api python -m pytest -q
